# Family Profiles v1 Scope

## Product decision

Family Profiles v1 is a **local household identity layer**, not profile sync.
It makes one Windows installation easier to share without changing Lights
Out's single-user LAN trust model or allowing another device to mutate local
profiles.

## User story

A household can create a small local member directory, assign saved bedtime
profiles to a member, filter the profile library by member, and see the member's
canonical identity on receipts generated by an explicit local start.

## In scope

- Create, rename, reorder, and delete local household members.
- Constrained member identity: generated ID, display name, avatar, and optional
  display-only accent from the existing safe palette.
- Assign zero or one household member to each saved profile.
- Filter the local profile library by household member.
- Preserve canonical member ID/name/avatar on timer state and receipts.
- Keep profile selection inert; assigning or selecting a member never starts a
  timer.
- Reconcile deleted members safely by clearing orphaned profile assignments
  while retaining historical receipt text.
- Include the member directory and assignments in existing export/import data.

## Explicitly out of scope

- LAN or cloud profile synchronization.
- Remote creation, editing, deletion, or selection of profiles.
- Per-member authentication, passwords, permissions, or parental-control
  enforcement.
- Separate Windows accounts or separate encrypted data stores.
- Cross-device streak aggregation.
- Turning Quiet House or School Night into available Night Modes.

## Data and trust boundaries

- Member records stay in the existing local settings store.
- Renderer input carries only a member ID across the IPC boundary; main resolves
  the canonical member record before timer or receipt attribution.
- Remote/companion starts remain unattributed unless a later, separately scoped
  security model explicitly changes that rule.
- Deleting a member cannot rewrite historical receipts.

## Proof gates

1. Create two members and assign different profiles to each.
2. Filter profiles by member and verify unassigned profiles remain reachable.
3. Confirm member/profile selection stays idle.
4. Start locally and verify canonical member identity reaches the receipt.
5. Attempt a forged renderer name with a valid ID and verify main ignores it.
6. Delete a member and confirm profile assignments reconcile without touching
   historical receipts.
7. Export/import and verify members plus assignments round-trip.
8. Confirm companion commands cannot attach or mutate member identity.

## Definition of done

The feature is complete only when the local member workflow, canonical identity
boundary, deletion reconciliation, export/import, accessibility, unit tests,
smoke coverage, and a real Electron interaction proof all pass.
